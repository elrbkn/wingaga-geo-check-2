# WinGaga — ежедневная проверка регистрации по гео

Автоматическая проверка: открывается реальный мобильный браузер, прокидывается прокси
нужной страны, проходится вся форма регистрации, и мы смотрим, что вернул сервер на
запрос `POST /api/v3/registration/signup`. Если пришёл блок Cloudflare (403 + HTML-страница
"Sorry, you have been blocked") — значит для этой страны регистрация недоступна, хотя
внешне на экране всё выглядит нормально.

Ниже — план "с нуля", по шагам, без пропусков. Если вы никогда не работали с Node.js —
не страшно, просто выполняйте пункты по порядку.

## Часть 1. Что установить на компьютер (один раз)

### 1.1 Node.js

Node.js — это программа, которая умеет выполнять JavaScript-код вне браузера. Наш тест
написан на JavaScript, поэтому без неё не запустится.

1. Зайдите на https://nodejs.org
2. Скачайте версию **LTS** (слева, с пометкой "Recommended for most users")
3. Установите как обычную программу (Next → Next → Install)
4. Проверьте, что всё встало: откройте терминал (на Windows — `cmd` или PowerShell,
   на Mac — `Terminal`) и введите:

   ```
   node -v
   npm -v
   ```

   Должны появиться номера версий (например `v20.11.0` и `10.2.4`). Если пишет
   "command not found" — переустановите Node.js и перезапустите терминал.

1. Скачайте на https://code.visualstudio.com

## Часть 2. Создание проекта

### 2.1 Создайте папку проекта

В терминале:

```bash
mkdir wingaga-geo-check
cd wingaga-geo-check
```

### 2.2 Инициализируйте Node-проект

```bash
npm init -y
```

Эта команда создаст файл `package.json` — в нём хранится список библиотек, которые
использует проект.

### 2.3 Установите нужные библиотеки

Всё, что нужно — три пакета:

```bash
npm install -D @playwright/test @faker-js/faker dotenv
npx playwright install chromium
```

Что это такое, простыми словами:
- **@playwright/test** — библиотека, которая умеет открывать настоящий браузер (Chrome) и
  управлять им как человек: кликать, вводить текст, ждать загрузки. Она же умеет
  "подслушивать" сетевые запросы браузера — это нам и нужно, чтобы поймать 403.
- **@faker-js/faker** — генератор фейковых, но реалистичных данных (имена, адреса)
  под разные страны. Телефоны генерируются отдельно, по реальным шаблонам
  формата (см. `config/countries.js`), а не через Faker.
- **dotenv** — позволяет хранить пароли и логины прокси в отдельном файле, а не прямо
  в коде (это безопаснее).
- `npx playwright install chromium` — скачивает сам браузер Chromium, которым будет
  управлять Playwright.

## Часть 6. Как всё это работает (объяснение по шагам)

### 6.1 `config/countries.js` — список проверяемых стран

Здесь просто перечислены 7 стран (`AT/CH/BE/CZ/IT/SK/HU`) с их телефонными кодами и
локалями для генератора данных. Если понадобится добавить/убрать страну — меняете
только этот файл, остальной код трогать не нужно.

### 6.2 `utils/dataGenerator.js` — генератор тестовых данных

Для каждой страны генерирует:
- email вида `qa-xxxxxxx@localqa.com` (обязательное требование антифрода — домен
  должен быть именно `@localqa.com`)
- пароль, имя, фамилию, дату рождения (18+ лет), адрес, город, индекс, телефон —
  всё в формате, характерном для этой страны (через библиотеку Faker с нужной
  локалью)

### 6.3 `tests/registration.test.js` — основной тест

Что делает пошагово, для КАЖДОЙ страны из списка:

1. **Настраивает прокси** — берёт логин `package-346398-country-XX-opt-lookalike`
   (где `XX` — код страны) и открывает браузер, весь трафик которого идёт через
   этот прокси. Так эмулируется пользователь именно из этой страны.
2. **Мобильная эмуляция** — Playwright открывает браузер с профилем мобильного
   телефона (размер экрана, User-Agent), как на ваших скриншотах.
3. **Проверяет реальный IP** — заходит на `https://ipapi.co/json/` и смотрит,
   какая страна показана по IP. Если не совпадает с ожидаемой — тест сразу
   помечает страну как "проблема с прокси" и не идёт дальше (незачем тестировать
   регистрацию с неправильным IP).
4. **Открывает страницу регистрации** по вашей ссылке.
5. **Проходит форму**: "Choose Casino" → "Choose" → заполняет email/пароль →
   "Next step" → заполняет имя/фамилию/дату рождения/пол/город/адрес/индекс/телефон
   → "Create account".
6. **Слушает сеть**: пока идёт весь этот процесс, в фоне работает "слушатель",
   который ждёт конкретный запрос `POST .../registration/signup` и запоминает,
   какой код ответа пришёл и что было в теле ответа.
7. **Классифицирует результат**:
   - `SUCCESS` — код 200/201, регистрация прошла
   - `CLOUDFLARE_EDGE_BLOCK` — код 403, ответ пришёл от Cloudflare (не от
     приложения) — это и есть целевая проблема "гео тихо заблокировано"
   - `APP_LEVEL_REJECTION` — код 403/400, но ответ в формате JSON от самого
     приложения (например, антифрод SEON отклонил заявку по другой причине)
   - `NO_REQUEST` / `TIMEOUT` — кнопку нажали, а запрос вообще не ушёл или завис
8. **Сохраняет доказательства**: скриншот финального экрана, `cf-ray` (ID
   конкретного инцидента в Cloudflare — пригодится, если будете разбираться с
   администраторами WAF), фрагмент тела ответа.
9. Переходит к следующей стране.

В конце сохраняется общий JSON-отчёт в `reports/report-ГГГГ-ММ-ДД.json` и (если
настроен Slack) уведомление, если хотя бы одна страна попала в
`CLOUDFLARE_EDGE_BLOCK`.

### 6.4 `.github/workflows/daily-check.yml` — автозапуск каждый день

Это файл для **GitHub Actions** — бесплатного облачного сервиса от GitHub, который
может сам, по расписанию, запускать ваш код на своём сервере (вам не нужно держать
свой компьютер включённым). Настроен на ежедневный запуск в 08:00 по UTC.

## Часть 8. Как поставить на ежедневный автозапуск

Есть два способа — выберите тот, который проще для вас.

### Способ А — GitHub Actions (рекомендуется, бесплатно, не нужен свой сервер)

1. Создайте пустой репозиторий на https://github.com (кнопка "New repository")
2. Внутри папки проекта выполните:

   ```bash
   git init
   git add .
   git commit -m "initial setup"
   git branch -M main
   git remote add origin https://github.com/ВАШ_АККАУНТ/ВАШ_РЕПОЗИТОРИЙ.git
   git push -u origin main
   ```

3. В настройках репозитория на GitHub зайдите в
   **Settings → Secrets and variables → Actions → New repository secret**
   и добавьте туда те же переменные, что в вашем `.env`:
   - `SOAX_PASSWORD`
   - `REGISTRATION_URL`
   - `SLACK_WEBHOOK_URL` (если используете)

   Это делается, чтобы пароль от прокси не лежал в открытом коде — GitHub хранит
   такие секреты зашифрованными.

4. Файл `.github/workflows/daily-check.yml` уже настроен на запуск каждый день —
   больше ничего делать не нужно. Проверить, что расписание работает, можно во
   вкладке **Actions** вашего репозитория.

### Способ Б — свой сервер / компьютер с cron (Linux/Mac)

Если у вас есть сервер, который работает 24/7:

```bash
crontab -e
```

Добавьте строку (запуск каждый день в 8:00 утра):

```
0 8 * * * cd /путь/до/wingaga-geo-check && npx playwright test >> reports/cron.log 2>&1
```

На Windows для этого используется "Планировщик заданий" (Task Scheduler) — там
нужно указать команду `npx playwright test` и задать расписание через интерфейс.

## Часть 10. Что изменилось в этой версии (важно прочитать)

По итогам первого прогона нашлись и исправлены следующие проблемы:

1. **Faker падал на некоторых локалях** (`Switzerland` и др.) с ошибкой
   "locale data ... are missing" — запасная локаль `base` оказалась неполной.
   Заменена на `en` — теперь если в целевой локали чего-то не хватает,
   подставляется английский вариант вместо падения теста.

2. **Тест зависал на 60 секунд для Austria и Belgium** — причина в том, что
   Playwright по умолчанию запускал браузер в headless-режиме через
   облегчённый `chrome-headless-shell`, у которого нет доступа к GPU
   ("No available adapters"). Cloudflare Turnstile (невидимая антибот-
   проверка, встроенная в форму) использует WebGL-сигналы и, судя по всему,
   никогда не завершался в таком окружении — форма Шага 2 просто не
   появлялась. **Исправление:** в `playwright.config.js` включён
   `headless: false` (полноценное окно браузера) + флаги программного
   WebGL-рендера (`--use-gl=swiftshader`). Это должно помочь Turnstile
   пройти нормально — как в вашем ручном тесте с обычным Chrome.

   ⚠️ Это не 100%-гарантированное решение — Turnstile может со временем
   ужесточить проверки. Если зависания повторятся даже с headed-режимом,
   самый надёжный путь — попросить администратора Cloudflare на стороне
   WinGaga добавить bypass-правило для IP/User-Agent вашего тестового
   окружения (стандартная практика для синтетического мониторинга).

3. **Баннер согласия на cookies не обрабатывался** — на сайте есть кнопка
   `data-testid="btnAcceptCookies"`, которая могла перекрывать форму и
   мешать кликам. Тест теперь пытается закрыть баннер сразу после захода
   на страницу (если баннера нет — просто пропускает этот шаг, ошибки не
   будет).

4. **Чекбоксы согласий больше не считаются "уже отмеченными" по умолчанию** —
   тест теперь явно проверяет состояние каждого чекбокса и отмечает те,
   что не отмечены, вместо того чтобы полагаться на то, как выглядело на
   скриншоте.

5. **Добавлено логирование зеркала и локали** — сайт может редиректить на
   разные домены в зависимости от гео (`wingaga354763.com/en/`,
   `wingaga7.com/cs/` и т.п.). Теперь в отчёте по каждой стране видно, на
   каком именно домене и локали был выполнен прогон (`landingDomain`,
   `landingLocale`), а также что фактически показали поля Country/Currency
   в самой форме (`detectedCountryField`, `detectedCurrencyField`) — удобно
   для сверки с ожидаемым гео.

6. **GitHub Actions обновлён под headed-режим** — так как `headless: false`
   не может работать на сервере без монитора, в workflow добавлена
   установка виртуального дисплея `xvfb`, и команда запуска теста обёрнута
   в `xvfb-run`.

7. **Прокси переведён на sticky session вместо обычной ротации.** Раньше
   логин прокси был вида `package-346398-country-at-opt-lookalike` — IP мог
   негласно меняться в процессе одного прогона. Теперь используется формат
   со "прилипающей" сессией:

   ```
   package-346398-country-at-sessionid-XXXXXXXXXXXXXXXX-sessionlength-600-bindttl-30-opt-lookalike
   ```

   - `sessionid` — генерируется случайно **на каждый запуск теста заново**
     (в коде, функцией `generateSessionId()`), поэтому IP каждый день свежий
   - `sessionlength-600` — держит один и тот же IP до 10 минут, этого с
     запасом хватает на весь флоу одной страны
   - `bindttl-30` — поддерживает привязку к этому IP каждые 30 секунд

   Это устраняет риск, что IP поменяется посреди прохождения формы (что
   само по себе выглядело бы подозрительно для антифрода), и одновременно
   не даёт тесту застревать на одном и том же адресе изо дня в день, если
   тот случайно попадёт под подозрение Cloudflare. Итоговый `sessionId`
   каждого прогона сохраняется в отчёте (`proxySessionId`) — пригодится,
   если понадобится обратиться в поддержку SOAX по конкретному IP.

## Часть 11. Частые вопросы

**Q: Тест показывает `PROXY_GEO_MISMATCH` для всех стран.**
A: Значит прокси не подключается правильно. Проверьте логин/пароль в `.env`,
и что порт/хост верные (`proxy.soax.com:5000`).

**Q: Как добавить ещё одну страну в проверку?**
A: Откройте `config/countries.js`, добавьте новую строку по образцу существующих.
Больше ничего менять не нужно.

**Q: Playwright ругается "Executable doesn't exist".**
A: Забыли выполнить `npx playwright install chromium` — сделайте это ещё раз.

**Q: Как посмотреть, что было заблокировано вчера?**
A: Все отчёты сохраняются в папке `reports/` с датой в названии файла — они не
перезаписываются.

## Часть 12. Критические баги в логике теста (найдено по реальному прогону)

После первого полного прогона (7/7 "passed") стало понятно, что тест **врал** —
Austria и Belgium физически не должны проходить регистрацию, но показались
зелёными. Разбор трейса выявил три самостоятельных бага:

1. **Финальная проверка засчитывала "passed" почти всегда.** Было:
   `expect(classification).not.toBe('CLOUDFLARE_EDGE_BLOCK')` — то есть тест
   падал только при одной конкретной классификации, а любая другая ошибка
   (включая обычный `TEST_ERROR` от таймаута) молча считалась успехом.
   Исправлено на строгое `expect(classification).toBe('SUCCESS')` — теперь
   успешным считается только точное совпадение.

2. **Перехватчик сети слушал только финальный `POST /registration/signup`.**
   Если реальная блокировка гео срабатывает раньше в цепочке запросов
   (например, на переходе к шагу с личными данными), тест её не видел и
   просто зависал на `fill()`, списывая это на "техническую ошибку".
   Теперь слушается **любой** ответ с кодом ≥400 на любом вызове `/api/`
   на протяжении всего прогона — где бы блок ни сработал, он будет пойман.

3. **Ветка `PROXY_GEO_MISMATCH` делала `return` до финальной проверки** —
   Playwright в таком случае вообще не видел assert и считал тест
   "passed" по умолчанию. Заменено на `throw`, чтобы выполнение всегда
   доходило до финальной проверки через `catch`/`finally`.

### Дополнительно (по вашим уточнениям к шагам 6 и 6)

4. **Проверка на видимые ошибки валидации** перед финальным кликом — если
   форма подсветила "This field is mandatory" или похожее, тест это
   зафиксирует явно (`FORM_VALIDATION_ERROR`) и не станет слепо жать
   "Create Account".

5. **UI-подтверждение реального логина** — даже если API ответил 2xx,
   тест дополнительно проверяет, что модалка регистрации закрылась
   (по вашему описанию: успех = автологин + касса). Если API сказал "ОК",
   а UI не подтвердил — классификация `SUCCESS_UNCONFIRMED_UI`, тест
   всё равно красный.

6. **Генератор телефона** — поле на форме уже показывает код страны как
   несъёмный префикс, а мы раньше дописывали его ещё раз внутри значения
   (получалось что-то вроде задвоенного кода), из-за чего валидация могла
   не проходить. Теперь генерируется только локальная часть номера.

После этих исправлений тест должен честно показывать красным именно те
страны, где регистрация реально не проходит — включая, скорее всего,
Austria и Belgium, если блокировка там действительно есть на момент
проверки.

## Часть 13. Фикс формата телефона (два захода)

**Первый заход** (генерация через `libphonenumber-js`) не до конца решил
проблему — при повторном прогоне поле Phone снова "поломалось". Перешли на
более надёжный вариант.

**Текущий подход:**

1. **Реальные шаблоны номеров вместо генерации "с нуля".** В
   `config/countries.js` для каждой страны добавлено поле `phoneTemplate` —
   заведомо корректный по формату номер (национальная часть, без кода
   страны). Уникальность номера форма, судя по всему, не проверяет, поэтому
   при каждой попытке меняются только **последние 3 цифры** шаблона — формат,
   длина и первый значащий блок (то, что и проверяет валидация) остаются
   нетронутыми. Если понадобится обновить шаблон для какой-то страны —
   меняется только этот файл.

2. **Посимвольный ввод** (`.pressSequentially()`) вместо `.fill()` — печатает
   по одному символу, как реальный пользователь; более надёжно работает с
   замаскированными полями.

3. **Двойная проверка результата после ввода:**
   - явный текст ошибки формата рядом с полем (как и раньше);
   - **сверка того, что реально осталось в поле**, с тем, что вводили
     (`inputValue()` после ввода) — это ловит "молчаливую" порчу значения
     (как в скриншоте с `+297` вместо `+420`), даже если сайт не показал
     никакой видимой ошибки.

   Если сработало любое из двух — тест очищает поле и пробует новый номер
   (до 4 попыток). Если не помогло ни разу — явно падает с классификацией
   `PHONE_FORMAT_ERROR`.

Зависимость `libphonenumber-js` в этой версии убрана за ненадобностью —
переустанавливать `npm install` из-за неё больше не нужно (но если у вас
уже стоит версия с ней из прошлого шага — она просто останется неиспользуемой,
это не помешает).
